2. Technology stack

The stack I recommend, and what each piece teaches you.

JWT is not a password-hashing algorithm

JWTs represent signed claims about a user or session. Password hashing protects stored passwords. We’ll learn both separately.

Passwords

We’ll use a dedicated password-hashing algorithm such as Argon2id or bcrypt, with an appropriate configuration.

Database access

We start with parameterized SQL queries using pg, so you understand SQL and database behavior before an ORM. We can consider Prisma later, once tables, joins, relationships, and transactions make sense.

3. Understand the system before writing code

Before coding, let’s see how the application will work.

3.1 User registration and email verification

Suppose a new user registers with this request body:

Request body
{
  "name": "Birendra Singh",
  "email": "birendra@example.com",
  "password": "MyStrongPassword123!"
}

The registration process

  1. The user sends a registration request.
  2. Express receives the request.
  3. TypeScript defines the expected data types, while runtime validation checks the actual input.
  4. The server checks whether the email is already registered.
  5. The password is hashed.
  6. The user is created in PostgreSQL with email_verified = false.
  7. The server generates a secure, temporary verification token.
  8. An email containing a verification link is sent.
  9. The user opens the link.
  10. The server verifies the token, checks its expiration, and marks the email as verified.

The user can then log in, provided the account meets the login requirements.

Important security decision

We will not store plaintext passwords or raw verification secrets in the database. We store a password hash and a hash of the verification token.

We’ll also consider what happens if email delivery fails after a user is created. We can build a resend-verification endpoint and later use a background job queue for more reliable delivery.

3.2 Login and JWT authentication

After verifying their email, the user logs in.

POST /api/auth/login · Content-Type: application/json
{
  "email": "birendra@example.com",
  "password": "MyStrongPassword123!"
}

The server will

  1. Find the user by email.
  2. Verify the submitted password against the stored password hash.
  3. Check whether the account is active and eligible to log in.
  4. Create a short-lived access token.
  5. Establish a refresh-token session.
  6. Return the access token and the appropriate refresh mechanism.

Initially we use a short-lived JWT access token and a longer-lived refresh-token session.

An access token might contain claims like these

Illustrative payload, not a complete token
{
  "sub": "user-uuid",
  "role": "user",
  "iss": "user-management-api",
  "aud": "user-management-client"
}

The JWT is digitally signed. The server validates its signature, expiration, issuer, and audience on protected requests.

A signed JWT is not encrypted

Anyone holding it can generally read its payload, so never put passwords, secrets, or other sensitive data inside it.

3.3 Accessing a protected profile

Request

Authentication versus authorization

Authentication: who are you?

Is this request associated with a valid authenticated user?

Authorization: what are you allowed to do?

Is this user allowed to delete another user’s account?

These are different security checks, and we’ll implement both.

4. Design the PostgreSQL database

One of the most important parts of the project. We design the database before building all the endpoints, so we don’t have to change it for every new feature. We’ll use UUID identifiers and explicit relationships.

4.1 Database tables

We start with five core tables and add more when the relevant features arrive.

TablePurpose
usersStores user profiles and account status
rolesDefines roles such as user and admin
user_rolesConnects users with their roles
email_verification_tokensTracks email verification tokens
refresh_tokensTracks refresh-token sessions

Later we’ll add tables for password resets, audit logs, and email delivery jobs if needed.

Why separate the roles table?

For a very small app with exactly one role per user, a role column in users could work. A separate role model is more flexible: one user might eventually have both user and support roles. So we use a many-to-many relationship.

usersid (PK)email
1many
user_rolesuser_id (FK)role_id (FK)
many1
rolesid (PK)name (unique)

A user can have multiple roles, and a role can belong to multiple users. This also teaches you an important relational concept: junction tables.

Email is unique and not nullable. Valid account statuses:

pending active suspended deactivated

These represent different account states, so we’ll define clear rules for how each one affects login and API access.

Why UUID instead of an auto-incrementing integer?

Both are valid. An integer is simple and efficient; UUIDs are useful when identifiers are generated across multiple services. UUIDs are not a substitute for authorization: knowing or guessing a user’s identifier must never grant access to that user’s data. We’ll use UUIDs to practise a common API design.

4.3 The roles table

idname
1user
2admin

The real table uses a primary key and a unique constraint on the role name. user_roles connects the two tables with foreign keys.

4.4 The email verification table

ColumnPurpose
idUnique record identifier
user_idUser who requested verification
token_hashHash of the verification secret
expires_atExpiration timestamp

Why expires_at? If someone requests a verification link and never opens it, it shouldn’t stay valid forever. We also make sure a token can be used only once.

4.5 The refresh-token table

This table helps manage user sessions. We store:

  • Session identifier
  • User identifier
  • Hash of the refresh token
  • Expiration timestamp
  • Revocation timestamp
  • Creation timestamp

When a user logs out, we revoke the refresh-token session. We also implement refresh-token rotation: when a refresh token is used, the old one is invalidated and a new one is issued. That gives more control than a long-lived access token that can’t easily be revoked.

A note about database security

Primary keys and foreign keys
Unique constraints for email addresses
Parameterized SQL queries
Transactions when several operations must succeed together
Indexes for commonly queried columns
Database migrations to manage schema changes

We’ll learn each of these by implementing it, not just by reading definitions.

5. Admin panel functionality and authorization

Two primary roles: user and admin. A normal user can access their own profile but not administer other accounts. An administrator can manage user accounts and send administrative emails.

Endpoints

MethodEndpointAccessPurpose

The admin user list uses pagination instead of returning every record in one response.

How will admin authorization work?

Suppose a regular user sends this:

Request
DELETE /api/admin/users/123
Authorization: Bearer <valid-user-token>

The token might be valid, but that doesn’t mean the user may delete accounts. Our middleware chain:

TypeScript
router.delete(
  "/users/:id",
  authenticate,
  authorize("admin"),
  deactivateUser
);
  • authenticate checks the identity associated with the access token.
  • authorize("admin") checks whether the authenticated user has the required role.
  • deactivateUser performs the operation.

This shows the intended structure; we’ll implement and type these functions together.

No self-promotion

Ordinary users must not be able to assign themselves the admin role by changing a request body. Role assignment is restricted to trusted administrative operations.

Soft deletion first

For account deletion we initially use soft deletion or deactivation instead of removing the row. That preserves audit history and lets us revoke sessions. Later we’ll discuss when permanent deletion is appropriate.

6. How will we secure the API?

Security isn’t a single middleware. It’s a collection of controls that protect different parts of the application, and we implement them gradually.

Password security

Never store a password like this:

Never do this
{
  "email": "birendra@example.com",
  "password": "MyStrongPassword123!"
}

Instead, the database holds a password hash, for example:

Stored value
password_hash = "$argon2id$..."

The password-hashing library generates the actual hash. During login, the application verifies the submitted password against it. It never decrypts the hash, because hashes aren’t meant to be decrypted.

JWT security

  • Sign tokens using a strong secret or private key.
  • Verify tokens using the correct key and algorithm.
  • Validate token expiration, issuer, and audience.
  • Keep access tokens short-lived.
  • Rotate and revoke refresh tokens.
  • Reject malformed or invalid tokens.
  • Avoid placing sensitive information inside JWT payloads.

For browser clients we’ll choose carefully how tokens are stored and sent. If we use cookies for refresh tokens, we configure HttpOnly, Secure, and appropriate SameSite settings, while also considering CSRF protection. We’ll avoid blindly storing long-lived authentication tokens in browser localStorage.

SQL injection protection

This is unsafe, because user input is inserted directly into the SQL string:

Unsafe
const query = `
  SELECT * FROM users
  WHERE email = '${email}'
`;

Instead, use a parameterized query:

Safe
const result = await pool.query(
  "SELECT id, email FROM users WHERE email = $1",
  [email]
);

PostgreSQL treats the supplied email as a parameter, not executable SQL. We use parameterized queries throughout the project.

Request validation

TypeScript doesn’t automatically validate incoming JSON. A client can send:

Invalid request
{
  "name": 12345,
  "email": "not-an-email",
  "password": false
}

Even if our interface says name must be a string, that doesn’t make the request valid. We use Zod to validate data at runtime before processing it.

We validate:

  • Email format
  • Password requirements
  • Required fields
  • String lengths
  • UUID parameters
  • Pagination parameters
  • Allowed values for account updates

We also avoid accepting arbitrary fields in sensitive requests.

Rate limiting

Suppose an attacker repeatedly submits login requests with different passwords. A rate limiter restricts how often a client can call an endpoint. We apply different limits to different operations:

Endpoint categoryProtection
LoginStrict rate limiting
RegistrationRate limiting and abuse prevention
Email verificationRate limiting
Password resetStrict rate limiting
General APIReasonable request limits
Admin endpointsAuthentication, authorization, and rate limiting

For a single-server learning environment, an in-memory limiter is enough to understand the concept. In a multi-instance deployment we use a shared store such as Redis, or a gateway-level limiter. Otherwise each server keeps its own counter and allows more requests than intended.

Other security controls

  • HTTPS in production
  • Secure CORS configuration
  • Appropriate security headers
  • Request-size limits
  • Protection against brute-force attacks
  • Generic authentication error messages where appropriate
  • Secrets in environment variables or a secrets manager
  • Least-privilege database accounts
  • Database connection timeouts
  • Dependency vulnerability checks
  • Audit logging for sensitive admin actions
  • Protection against email enumeration and abuse
  • Graceful error handling without exposing stack traces
Keep internals hidden

Admin endpoints must not expose password hashes, verification tokens, refresh tokens, or other internal security information.

7. What if 100,000 requests arrive at the same time?

An excellent question, because it takes us beyond basic CRUD APIs into backend engineering. First, we need to clarify what “at the same time” means.

1

100,000 requests arrive in a few seconds.

2

100,000 requests are actively in progress.

3

100,000 users remain connected simultaneously.

4

100,000 requests per second.

These are very different workloads. We can’t assume a server handles all of them just because it uses Node.js. Our goal: build a correct application first, then measure it and improve its capacity.

7.2 Node.js handles I/O asynchronously

Node.js suits applications that spend much of their time waiting on database queries, network responses, email provider responses, and file and network I/O.

TypeScript
const result = await pool.query(
  "SELECT id, name, email FROM users WHERE id = $1",
  [userId]
);

While the query waits for a response, Node.js can process other eligible work. But async and await don’t make every operation faster, and they don’t create unlimited capacity. CPU-intensive work can block the event loop, and a database can be overloaded even when Node.js looks healthy.

7.3 Use a PostgreSQL connection pool

Suppose 10,000 requests arrive and each opens a new database connection. That can overwhelm PostgreSQL and waste resources. Instead we use a pool.

10,000 API requests
Connection Pool
Connection 1
Connection 2
Connection 3
… Connection N
PostgreSQL

The pool limits simultaneous database connections from that instance. Requests wait for a free connection when the pool is busy. We configure and measure the pool rather than choosing a large number arbitrarily, and we’ll see why more connections can make performance worse if PostgreSQL is already saturated.

7.4 Use caching carefully

Some data is requested often but changes rarely, such as role definitions or certain public configuration. Redis can cache selected data and support shared rate limiting and background-job infrastructure.

Don’t cache everything

User permissions, account status, and other security-sensitive data need careful invalidation and consistency decisions.

7.5 Move slow work into background jobs

Imagine an administrator wants to email 50,000 users. If the API sends every email before responding, the request can take a long time and time out. Instead:

  1. Admin submits email campaign
  2. API validates request
  3. Job added to queue
  4. API returns job ID
  5. Background workers process jobs
  6. Email provider sends messages

We’ll introduce a queue such as BullMQ with Redis, and cover retries, exponential backoff, duplicate-job prevention, delivery failures, and email-provider limits. A queue controls the rate at which work is processed; it doesn’t make the provider able to send unlimited messages.

Instances must be designed to work together. If one stores rate-limit counters or login sessions only in its own memory, another won’t know about them. That’s why shared infrastructure matters. We’ll also cover indexes, query optimization, load testing, monitoring, horizontal scaling, and the limits of simply adding servers.

What will we use to test performance?

A tool such as k6 or autocannon. We’ll measure:

Requests per second
Median response time
95th- and 99th-percentile response times
Error rate
CPU and memory usage
Database connection-pool saturation
PostgreSQL query performance

We’ll increase the workload gradually and observe what fails first.

The important lesson

We won’t claim our API can handle 100,000 simultaneous requests until we’ve defined the workload, tested it, and measured the results on a known environment.
