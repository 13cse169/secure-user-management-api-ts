Phase 4: User registration

We build an API that lets a new user register with their name, email, and password, with validation, secure password hashing, and proper duplicate-email handling.

4.1

Create the registration validation schema

Before accepting registration data, we must validate it. For example, we should reject:

  • Empty names
  • Invalid email addresses
  • Passwords that don’t meet our requirements
  • Missing request fields

We validate before the controller or database receives the data.

1. Create the validators folder

src/
validators/
auth.validator.ts

2. Create the registration schema

src/validators/auth.validator.ts
import { z } from "zod";

export const registerSchema = z.object({
  name: z
    .string()
    .trim()
    .min(2, "Name must contain at least 2 characters")
    .max(100, "Name cannot exceed 100 characters"),

  email: z
    .string()
    .trim()
    .email("Please enter a valid email address")
    .max(255, "Email cannot exceed 255 characters")
    .transform((value) => value.toLowerCase()),

  password: z
    .string()
    .min(12, "Password must contain at least 12 characters")
    .max(128, "Password cannot exceed 128 characters")
});

3. Understand each validation

ValidationMeaning
z.object()Defines an object schema
z.string()Accepts only strings
.trim()Removes leading and trailing spaces
.min(2)Requires at least 2 characters
.max(100)Allows at most 100 characters
.email()Checks email format
.transform()Converts email to lowercase
Password rules

For passwords, we require at least 12 characters and limit the maximum to 128. We’re not forcing special characters or uppercase letters. A sufficiently long, unique password or passphrase is a better goal than arbitrary character rules.

4. Understand safeParse()

Zod provides two important methods:

parse()

Validates data and throws an error if validation fails.

safeParse()

Validates data and returns a success or failure result without throwing a validation error.

4.2

Create reusable validation middleware

1. Why do we need validation middleware?

Imagine we have three APIs that all receive data from the client and need validation:

  • POST /api/auth/register
  • POST /api/auth/login
  • PATCH /api/users/me

We could validate each request inside its controller, but that would duplicate code. Instead we create one reusable middleware. The request flow will look like this:

Client request
Validation middleware
Valid data → Controller: continue request
Invalid data → 400 response: stop request

The controller will receive validated data only.

2. Create the middleware file

src/middlewares/validate.middleware.ts
import type { RequestHandler } from "express";
import type { ZodType } from "zod";
import { sendResponse } from "../utils/api-response.js";

export const validate = (schema: ZodType): RequestHandler => {
  return (req, res, next) => {
    const result = schema.safeParse(req.body);

    if (!result.success) {
      const errors = result.error.issues.map((issue) => ({
        field: issue.path.join("."),
        message: issue.message
      }));

      sendResponse(
        res,
        400,
        "Validation failed",
        errors
      );

      return;
    }

    req.body = result.data;

    next();
  };
};

3. Understand the code

A. Why do we pass schema as a parameter?
export const validate = (schema: ZodType): RequestHandler => {

This makes our middleware reusable. For registration we pass registerSchema; for login we’ll pass a future loginSchema. The same middleware works with both.

B. Why use safeParse()?
const result = schema.safeParse(req.body);

It checks the incoming request body against our Zod schema.

C. What happens when validation fails?
if (!result.success) {

We extract the validation errors and return a standard HTTP 400 response. Example:

{
  "success": false,
  "message": "Validation failed",
  "data": [
    {
      "field": "email",
      "message": "Please enter a valid email address"
    }
  ]
}
D. Why do we assign result.data to req.body?
req.body = result.data;

This is important! Remember that we used .trim() and .transform() in our Zod schema. For example, a client sends:

{
  "name": "  Birendra Singh  ",
  "email": "BIRENDRA@EXAMPLE.COM"
}

After validation, the controller receives:

{
  "name": "Birendra Singh",
  "email": "birendra@example.com"
}

So the controller gets the cleaned and validated data.

E. Why call next()?
next();

It tells Express that validation succeeded and it can continue to the next middleware or controller.

4.4

Create the registration service

Now we implement the actual registration logic:

  1. Receive validated user details.
  2. Hash the password using Argon2id.
  3. Insert the user into PostgreSQL.
  4. Return the newly created user’s public information.

First, one important security concept

We must never store a user’s original password in PostgreSQL.

FieldValue
Original passwordMySecurePassword@123
Stored passwordArgon2id hash

Even if someone accesses the database, they won’t see the original password. We also use parameterized SQL queries to protect against SQL injection.

Create src/services/auth.service.ts

src/services/auth.service.ts
import argon2 from "argon2";
import pool from "../config/db.js";

type RegisterInput = {
  name: string;
  email: string;
  password: string;
};

export const registerUser = async (userData: RegisterInput) => {
  const { name, email, password } = userData;

  // Step 1: Hash the password
  const passwordHash = await argon2.hash(password, {
    type: argon2.argon2id
  });

  // Step 2: Insert user into PostgreSQL
  const result = await pool.query(
    `INSERT INTO users (name, email, password_hash)
     VALUES ($1, $2, $3)
     RETURNING id, name, email, is_email_verified, is_active, created_at`,
    [name, email, passwordHash]
  );

  // Step 3: Return public user information
  return result.rows[0];
};

Understand the important parts

PartWhat it does
argon2.hash()Generates a secure password hash
argon2idThe recommended Argon2 variant for password hashing
$1, $2, $3PostgreSQL query parameters
RETURNINGGives us the newly inserted record
Selected columnsWe deliberately exclude password_hash from the returned data
Don’t connect it to the controller yet

We do that in a later step, after handling duplicate email errors properly.

Create a centralized application error handler

Before connecting registration to the controller, we need to handle duplicate email addresses properly. If someone registers using an email that already exists, the API should return:

1. Create src/utils/app-error.ts

export class AppError extends Error {
  constructor(
    public statusCode: number,
    message: string

    super(message);

    this.name = "AppError";
  }
}

2. Update the error handler

Replace the existing code in src/middlewares/error-handler.middleware.ts with:

import type { ErrorRequestHandler } from "express";
import { AppError } from "../utils/app-error.js";
import { sendResponse } from "../utils/api-response.js";

export const errorHandler: ErrorRequestHandler = (
  err,
  _req,
  res,
  _next
) => {
  console.error(err);

  if (res.headersSent) return;

  if (err instanceof AppError) {
    sendResponse(res, err.statusCode, err.message);
    return;
  }

  sendResponse(res, 500, "Internal server error");
};

4.6

Handle duplicate email registration

PostgreSQL already protects your email column with a unique index:

SQL (from Phase 3)
CREATE UNIQUE INDEX users_email_unique_idx
ON users (LOWER(email));

This is important because two users might try to register with the same email at almost exactly the same time. PostgreSQL returns error code 23505 when a unique constraint is violated. We catch that error and convert it into our custom AppError.

1. Update src/services/auth.service.ts

Replace your existing registration function with:

src/services/auth.service.ts
import argon2 from "argon2";
import pool from "../config/db.js";
import { AppError } from "../utils/app-error.js";

type RegisterInput = {
  name: string;
  email: string;
  password: string;
};

export const registerUser = async (userData: RegisterInput) => {
  const { name, email, password } = userData;

  const passwordHash = await argon2.hash(password, {
    type: argon2.argon2id
  });

  try {
    const result = await pool.query(
      `INSERT INTO users (name, email, password_hash)
       VALUES ($1, $2, $3)
       RETURNING id, name, email, is_email_verified, is_active, created_at`,
      [name, email, passwordHash]
    );

    return result.rows[0];
  } catch (error: unknown) {
    if (
      typeof error === "object" &&
      error !== null &&
      "code" in error &&
      error.code === "23505"
    ) {
      throw new AppError(409, "Email address is already registered");
    }

    throw error;
  }
};

2. Understand the important part

catch (error: unknown)

We use unknown because TypeScript should not assume every caught value is an Error object.

error.code === "23505"

This checks PostgreSQL’s unique-violation error code.

throw new AppError(409, ...)

This passes our custom error to the global error handler.

One important detail

We hash the password before attempting the insert. A duplicate registration may therefore use some extra CPU for hashing, but the database remains the final authority on uniqueness. We can optimize this later if needed.

4.7

Create the registration controller

The controller receives the validated request, calls the registration service, and returns a standardized API response.

1. Create src/controllers/auth.controller.ts

src/controllers/auth.controller.ts
import type { Request, Response, NextFunction } from "express";
import { registerUser } from "../services/auth.service.js";
import { sendResponse } from "../utils/api-response.js";

export const register = async (
  req: Request,
  res: Response,
  next: NextFunction
): Promise<void> => {
  try {
    const user = await registerUser(req.body);

    sendResponse(
      res,
      201,
      "Registration successful. Please verify your email.",
      user
    );
  } catch (error) {
    next(error);
  }
};
Why 201?

HTTP 201 Created indicates that a new resource has been successfully created.

2. Update src/routes/auth.routes.ts

Replace the temporary callback with the real controller:

src/routes/auth.routes.ts
import { Router } from "express";

import { registerSchema } from "../validators/auth.validator.js";
import { register } from "../controllers/auth.controller.js";

const router = Router();

router.post("/register", validate(registerSchema), register);

export default router;
