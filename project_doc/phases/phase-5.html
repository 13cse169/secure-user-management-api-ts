Overview / Phase 5

Phase 5: Email verification

We add two-step email verification: secure, time-limited tokens, stored as hashes, delivered by email, and verified through a dedicated endpoint.

Goal

Verify email addresses before allowing normal login.

Deliverable

Users can register and verify their email.

Flow

How verification will work

The registration flow will eventually work like this:

  1. User submits registration details.
  2. API creates an unverified user.
  3. API generates a secure verification token.
  4. API sends a verification email.
  5. User clicks the verification link.
  6. API verifies the token and activates email verification.

We’ll first design the database table email_verification_tokens before writing the email-sending logic.

  user_id BIGINT NOT NULL,

  expires_at TIMESTAMPTZ NOT NULL,

  used_at TIMESTAMPTZ,

3. Understand each column

ColumnPurpose
idUnique token record ID
user_idLinks token to a user
token_hashStores hashed verification token
expires_atToken expiration time
used_atRecords when token was used
created_atToken creation timestamp
Why store a hash instead of the original token?

Suppose an attacker accesses your database. If you store the original verification token, they could use it to verify someone else’s email. By storing only its hash, the original token cannot be directly retrieved from the database.

5.2

Generate a secure verification token

We generate a cryptographically secure random token using Node.js’s built-in crypto module.

Why crypto?

We should never use Math.random() for authentication or verification tokens. It isn’t designed for security. Node.js provides crypto.randomBytes() for generating unpredictable random bytes.

1. Create the token utility

src/utils/token.ts
import { createHash, randomBytes } from "node:crypto";

export const generateVerificationToken = () => {
  // Generate 32 cryptographically secure random bytes
  const token = randomBytes(32).toString("hex");

  // Generate SHA-256 hash of the token
  const tokenHash = createHash("sha256")
    .update(token)
    .digest("hex");

  return {
    token,
    tokenHash
  };
};

2. Understand the code

A. Generate the original token
const token = randomBytes(32).toString("hex");
  • randomBytes(32) generates 32 random bytes.
  • .toString("hex") converts them into a hexadecimal string.
  • The result contains 64 hexadecimal characters.
B. Generate its hash
const tokenHash = createHash("sha256").update(token).digest("hex");

This creates a SHA-256 hash of the original token.

C. Return both values
return {
  token,
  tokenHash
};

Remember which value goes where:

ValueWhere we use it
tokenSend to the user’s email
tokenHashStore in PostgreSQL
Never leak the original token

Never store the original token in the database or log it in the terminal.

5.3

Store the verification token in PostgreSQL

Now we create a service that stores the token hash and sets its expiration time to 15 minutes.

1. Create the service

src/services/email-verification.service.ts
import pool from "../config/db.js";
import { generateVerificationToken } from "../utils/token.js";

export const createVerificationToken = async (
  userId: string
): Promise<string> => {
  // Step 1: Generate token and hash
  const { token, tokenHash } = generateVerificationToken();

  // Step 2: Store hash in PostgreSQL
  await pool.query(
    `INSERT INTO email_verification_tokens
     (user_id, token_hash, expires_at)
     VALUES ($1, $2, NOW() + INTERVAL '15 minutes')`,
    [userId, tokenHash]
  );

  // Step 3: Return original token for email delivery
  return token;
};

2. Understand the important logic

Why do we return the original token?

The original token will eventually be included in the verification email link, for example:

https://yourwebsite.com/verify-email?token=ORIGINAL_TOKEN

The database stores only its hash.

Why use NOW() + INTERVAL '15 minutes'?

PostgreSQL calculates the expiration time using its own database clock. For example:

FieldExample
Created at10:00 AM
Expires at10:15 AM
Token statusUnused

After 10:15 AM, the token must not be accepted.

5.5

Implement PostgreSQL transactions

Before integrating email delivery, let’s fix an important database reliability issue.

The problem: registration performs two separate database operations.

  1. Insert user into users.
  2. Insert verification token into email_verification_tokens.

Imagine the user is inserted successfully, but token creation fails. The database would contain a registered user without a verification token. We want both operations to succeed together or fail together. That’s exactly what a database transaction provides.

1. Update src/services/email-verification.service.ts

We pass an existing database connection to this service instead of using the global connection pool. Replace the file with:

src/services/email-verification.service.ts
import type { PoolClient } from "pg";
import { generateVerificationToken } from "../utils/token.js";

export const createVerificationToken = async (
  userId: string,
  client: PoolClient
): Promise<string> => {
  const { token, tokenHash } = generateVerificationToken();

  await client.query(
    `INSERT INTO email_verification_tokens
     (user_id, token_hash, expires_at)
     VALUES ($1, $2, NOW() + INTERVAL '15 minutes')`,
    [userId, tokenHash]
  );

  return token;
};

2. Update src/services/auth.service.ts

Replace your existing registration service with:

src/services/auth.service.ts
import argon2 from "argon2";
import pool from "../config/db.js";
import { AppError } from "../utils/app-error.js";
import { createVerificationToken } from "./email-verification.service.js";

type RegisterInput = {
  name: string;
  email: string;
  password: string;
};

export const registerUser = async (userData: RegisterInput) => {
  const { name, email, password } = userData;

  // Hash password before opening the transaction
  const passwordHash = await argon2.hash(password, {
    type: argon2.argon2id
  });

  const client = await pool.connect();

  try {
    // Start transaction
    await client.query("BEGIN");

    // Insert user
    const result = await client.query(
      `INSERT INTO users (name, email, password_hash)
       VALUES ($1, $2, $3)
       RETURNING id, name, email, is_email_verified, is_active, created_at`,
      [name, email, passwordHash]
    );

    const user = result.rows[0];

    // Generate and store verification token
    const verificationToken = await createVerificationToken(
      String(user.id),
      client
    );

    // Commit transaction
    await client.query("COMMIT");

    return {
      user,
      verificationToken
    };

  } catch (error: unknown) {
    await client.query("ROLLBACK");

    if (
      typeof error === "object" &&
      error !== null &&
      "code" in error &&
      error.code === "23505"
    ) {
      throw new AppError(409, "Email address is already registered");
    }

    throw error;

  } finally {
    client.release();
  }
};

3. Understand the transaction flow

BEGINStart transaction
INSERT USER
INSERT VERIFICATION TOKEN
Success → COMMIT: save both records
Failure → ROLLBACK: undo both operations

Important concepts:

ConceptWhat it means
pool.connect()Obtains one database connection
Same clientAll transaction queries must use that same client
COMMITSaves the changes
ROLLBACKCancels the changes
client.release()Returns the connection to the pool

6. Understand the code

This function is an asynchronous arrow function with an explicit return type. Let’s break it into five parts.

1. variableconst testEmailConnection
2. keyword= async
3. parameters()
4. return type: Promise<void>
5. body=> { }
1. const testEmailConnection

We are declaring a variable named testEmailConnection. This variable will hold a function. Similar to JavaScript:

const greet = () => {
  console.log("Hello");
};
2. = async

The async keyword makes this an asynchronous function. Why do we need it? Because inside this function we call:

await transporter.verify();

The verify() method performs an asynchronous SMTP connection check. await allows JavaScript to wait for that operation to finish before continuing with the next statement. An async function always returns a Promise.

3. async ()

These parentheses represent function parameters. Our function doesn’t need any input, so we leave them empty. For example:

const greet = (name: string) => {
  console.log(`Hello ${name}`);
};

Here, name is a parameter. But our email connection test doesn’t require any parameters.

4. : Promise<void>

This is the most important TypeScript part. It tells TypeScript what the function returns. Let’s understand both words:

  • Promise: represents a value that may become available in the future because an asynchronous operation is still running.
  • void: means that the function does not return a meaningful value.

For example, this function prints something but doesn’t return a value:

const sayHello = (): void => {
  console.log("Hello");
};

Now combine them: Promise<void> means the function returns a Promise, and when that Promise successfully completes, it doesn’t provide a meaningful result.

5. => { }

This is the arrow function syntax. It starts the function body.

Let’s compare different function declarations

FunctionMeaning
(): voidSynchronous function with no meaningful return value
(): stringSynchronous function returning a string
async (): Promise<void>Async function with no meaningful return value
async (): Promise<string>Async function returning a string through a Promise

Practical example

Synchronous
const getName = (): string => {
  return "Birendra";
};
Asynchronous
const getName = async (): Promise<string> => {
  return "Birendra";
};

Although we return a string inside the async version, JavaScript wraps that value in a Promise. You can use it like this:

const name = await getName();

console.log(name);
Output

5.9

Implement the email verification service

We use a POST endpoint to verify the token. For now, we test it by copying the token from the email and sending it in the request body.

Why POST instead of verifying directly on GET?

Some email providers automatically open links to scan them. We don’t want an automatic link scan to verify an account without the user taking action.

1. Create the verification service

We already have createVerificationToken() in src/services/email-verification.service.ts. Keep that function and add the following imports at the top of the existing file:

src/services/email-verification.service.ts
import { createHash } from "node:crypto";
import pool from "../config/db.js";
import { AppError } from "../utils/app-error.js";

Keep your existing PoolClient import and createVerificationToken function. Now add:

src/services/email-verification.service.ts
export const verifyEmailToken = async (
  token: string
): Promise<void> => {
  // Step 1: Hash the received token
  const tokenHash = createHash("sha256").update(token).digest("hex");

  const client = await pool.connect();

  try {
    await client.query("BEGIN");

    // Step 2: Find a valid, unused, unexpired token
    const result = await client.query(
      `SELECT id, user_id
       FROM email_verification_tokens
       WHERE token_hash = $1
       AND used_at IS NULL
       AND expires_at > NOW()
       FOR UPDATE`,
      [tokenHash]
    );

    if (result.rowCount === 0) {
      throw new AppError(
        400,
        "Invalid or expired verification token"
      );
    }

    const verificationRecord = result.rows[0];

    // Step 3: Mark the user's email as verified
    await client.query(
      `UPDATE users
       SET is_email_verified = TRUE,
       updated_at = NOW()
       WHERE id = $1`,
      [verificationRecord.user_id]
    );

    // Step 4: Mark token as used
    await client.query(
      `UPDATE email_verification_tokens
       SET used_at = NOW()
       WHERE id = $1`,
      [verificationRecord.id]
    );

    await client.query("COMMIT");

  } catch (error) {
    await client.query("ROLLBACK");
    throw error;

  } finally {
    client.release();
  }
};

2. Understand the important concepts

CodePurpose
createHash("sha256")Hashes the token received from the user
expires_at > NOW()Rejects expired tokens
used_at IS NULLRejects previously used tokens
FOR UPDATELocks the selected token row during verification
is_email_verified = TRUEVerifies the user’s email
used_at = NOW()Prevents token reuse
Why FOR UPDATE?

Imagine two requests arrive simultaneously using the same token. Without row locking, both requests might read the token as unused. FOR UPDATE ensures that only one transaction can process that token at a time. The second request will see that the token has already been used after the first transaction commits.
