Overview / Phase 2

Phase 2: Routes, controllers, services, and middleware

Since Phase 1 is working, we transform the basic Express server into a well-organized backend application using TypeScript. Professional backends separate responsibilities instead of putting everything in one file.

We’ll build this incrementally on the existing Secure User Management API. You don’t need to understand every concept immediately: each file is explained along the way.

Goal

Understand how requests travel through our application.

Deliverable

A structured API with working routes, controllers, and validation-ready structure.

By the end you will understand

  • How an Express request travels through your application
  • What routes do
  • What controllers do
  • What services do
  • What middleware does
  • How centralized error handling works
  • How TypeScript helps us organize our code

Why separate files?

Imagine putting registration, login, JWT verification, email sending, and database queries into server.ts. That file would become difficult to understand, test, and maintain. Separating responsibilities lets us add features without turning the application into one large file.

3

Understand routes

A route defines which code runs when a particular HTTP request arrives, for example GET /api/users or POST /api/auth/login. In Express we write routes using:

Route methods
app.get();
app.post();
app.put();
app.patch();
app.delete();

A simple example:

Example
app.get("/api/users", (req, res) => {
  res.json({
    message: "Get all users"
  });
});
  • app.get() registers a GET route.
  • "/api/users" is the URL path.
  • req represents the incoming request.
  • res lets us send the response.

But we don’t want to define every route directly inside app.ts. Instead we create dedicated route files.

Step 3.1: Create src/routes/health.routes.ts

src/routes/health.routes.ts
import { Router } from "express";

import { getHealth } from "../controllers/health.controller.js";

const router = Router();

router.get("/", getHealth);

export default router;
Understand Router()
const router = Router();

This creates a separate router that can manage related endpoints.

The route itself
router.get("/", getHealth);

A GET request to the router’s root path executes the getHealth controller.

Why “/” and not “/api/health”?

We connect this router to /api/health in app.ts, and Express combines the two paths: /api/health + / = /api/health. We can change the base path in one place without rewriting every route.

4

Understand controllers

A controller handles the HTTP request and decides what response to send. For GET /api/health it might return:

Response
{
  "success": true,
  "message": "API is running"
}

A controller should generally handle HTTP-specific responsibilities rather than containing all our business logic.

Step 4.1: Create src/controllers/health.controller.ts

src/controllers/health.controller.ts
import type { Request, Response } from "express";

export const getHealth = (
  _req: Request,
  res: Response
): void => {
  res.status(200).json({
    success: true,
    message: "Secure User Management API is running"
  });
};

Let’s understand the types

Request
_req: Request

This represents the incoming HTTP request. It can contain:

  • URL parameters
  • Query parameters
  • Request headers
  • Request body
Response
res: Response

This represents the HTTP response we send to the client.

res.status(200).json({
  success: true,
  message: "API is running"
});

This sends a JSON response with HTTP status code 200.

Why return void?
): void => {

Our controller sends its response using res.status().json(). It doesn’t need to return a value to another function, so we specify void.

One important TypeScript lesson

Types such as Request and Response help us during development. They do not validate incoming JSON at runtime. We’ll learn runtime validation with Zod later.

5

Understand services

This is an important concept. A service contains the application’s business logic. As an example from a future feature, when a user registers we may need to:

  1. Check whether the email is already registered.
  2. Hash the password.
  3. Create the user in PostgreSQL.
  4. Generate a verification token.
  5. Save the token.
  6. Arrange for a verification email to be sent.

The controller should not implement all those operations itself. Instead it calls a registration service that coordinates the business logic. For now we use a simple example that returns sample users, so we learn the separation before introducing a database.

Step 5.1: Create src/services/user.service.ts

src/services/user.service.ts
export type User = {
  id: number;
  name: string;
  email: string;
};

const users: User[] = [
  {
    id: 1,
    name: "Birendra Singh",
    email: "birendra@example.com"
  },
  {
    id: 2,
    name: "Rahul Sharma",
    email: "rahul@example.com"
  }
];

export const getAllUsers = (): User[] => {
  return users;
};

What are we learning here?

First, a TypeScript type
export type User = {
  id: number;
  name: string;
  email: string;
};

A User has three properties: id must be a number, name a string, and email a string.

Then, sample data
const users: User[] = [
  // ...
];

The User[] notation means an array of User objects.

Finally, a function that returns the list
export const getAllUsers = (): User[] => {
  return users;
};
Temporary data

These are in-memory records. They disappear when the process restarts, and this isn’t our final database implementation. We replace it with PostgreSQL queries in a later phase.

Connect the controller to the service

Now the controller calls the service. Create src/controllers/user.controller.ts:

src/controllers/user.controller.ts
import type { Request, Response } from "express";

import { getAllUsers } from "../services/user.service.js";

export const getUsers = (
  _req: Request,
  res: Response
): void => {
  const users = getAllUsers();

  res.status(200).json({
    success: true,
    count: users.length,
    data: users
  });
};

Let’s follow the execution

  1. const users = getAllUsers(); The controller calls the service.
  2. The service returns the user array.
  3. res.status(200).json({ ... }) The controller sends the response to the client.

Route

Determines which controller handles the request.

Controller

Handles the HTTP request and response.

Service

Provides the application’s business logic.

When we introduce PostgreSQL, the controller won’t need to know how the users are stored. The service can obtain them from the database instead.

8

Understand middleware

Middleware is one of the most important concepts in Express. A middleware function runs during the request-response lifecycle. It can inspect a request, modify it, send a response, pass control to the next middleware, or forward an error.

Later we’ll create authentication middleware that checks whether a request contains a valid JWT. For now, a simple request logger.

Step 8.1: Create request-logger middleware

src/middlewares/request-logger.middleware.ts
import type { RequestHandler } from "express";

export const requestLogger: RequestHandler = (
  req,
  _res,
  next
) => {
  console.log(
    `${req.method} ${req.originalUrl} - ${new Date().toISOString()}`
  );

  next();
};
What is RequestHandler?
import type { RequestHandler } from "express";

Express provides a RequestHandler type for ordinary middleware and route handlers. We use it so TypeScript can check that our middleware has the expected function signature.

What does next() do?
next();

This tells Express to continue to the next applicable middleware or route handler. If you forget to call next() and don’t send a response, the request may remain pending.

Controller
Response
Middleware doesn’t always call next()

Authentication middleware, for example, should stop the request and return 401 Unauthorized when authentication fails.

9

Create 404 handling

Suppose someone visits GET /api/unknown. No route matches that URL, and we want a proper JSON error instead of an unexpected response.

src/middlewares/not-found.middleware.ts
import type { RequestHandler } from "express";

export const notFoundHandler: RequestHandler = (
  req,
  res,
  _next
) => {
  res.status(404).json({
    success: false,
    message: `Route not found: ${req.method} ${req.originalUrl}`
  });
};

We return 404 Not Found because the requested endpoint doesn’t exist. Notice we don’t call next() after sending the response: we handled the request, so there’s no reason to continue through the middleware chain.

10

Create centralized error handling

Imagine a controller tries to access PostgreSQL and the connection fails. We don’t want every controller to invent its own error-handling format. Instead we eventually route errors to a centralized error handler.

src/middlewares/error-handler.middleware.ts
import type { ErrorRequestHandler } from "express";

export const errorHandler: ErrorRequestHandler = (
  err,
  _req,
  res,
  _next
) => {
  console.error(err);

  if (res.headersSent) {
    return;
  }

  res.status(500).json({
    success: false,
    message: "Internal server error"
  });
};
Understand ErrorRequestHandler

Express error-handling middleware has four parameters: (err, req, res, next). The first is the error. Express recognizes error-handling middleware by this four-parameter signature.

Why return a generic error?

If a database query fails because of an internal configuration problem, we don’t want to expose:

  • Database credentials
  • Internal file paths
  • Stack traces
  • SQL statements containing sensitive information

We log the error on the server and return a generic message to the client. In production we’ll improve this with structured error logs, separate handling for expected errors, and logs that never expose secrets or sensitive user information.

What does res.headersSent do?

The check prevents us from trying to send a second response if headers have already been sent. In that situation, Express should be allowed to handle the error through its remaining error-handling mechanism.

Defining a handler isn’t enough

Merely defining an error handler doesn’t automatically route every possible error to it. Express 5 automatically forwards rejected promises from async route handlers; in other situations we may need to use next(err).

11

Update src/app.ts

Now we have our routes and middleware. Let’s connect everything. Replace your existing src/app.ts with:

src/app.ts
import express from "express";

import healthRouter from "./routes/health.routes.js";
import userRouter from "./routes/user.routes.js";

import { requestLogger } from "./middlewares/request-logger.middleware.js";
import { notFoundHandler } from "./middlewares/not-found.middleware.js";
import { errorHandler } from "./middlewares/error-handler.middleware.js";

const app = express();

// Parse incoming JSON
app.use(express.json());

// Log incoming requests
app.use(requestLogger);

// Register API routes
app.use("/api/health", healthRouter);
app.use("/api/users", userRouter);

// Handle unknown routes
app.use(notFoundHandler);

// Handle errors
app.use(errorHandler);

export default app;
Default exports

Our route files use default exports, so they are imported without curly braces (import healthRouter from ...). Use this complete version rather than a partial one that imports { healthRouter }.

Let’s understand the order

  1. JSON middleware. app.use(express.json()); parses incoming JSON bodies.
  2. Request logger. app.use(requestLogger); logs requests before they reach the routes.
  3. API routes. app.use("/api/health", healthRouter); and app.use("/api/users", userRouter); mount our two routers.
  4. 404 handler. app.use(notFoundHandler); handles requests that reach this point without matching an earlier route.
  5. Error handler. app.use(errorHandler); handles errors forwarded through Express’s error-handling mechanism.
Middleware order matters

If we registered the 404 handler before our routes, it would respond before those routes had a chance to handle requests.

Our server.ts can remain unchanged.

Use one standard response format

Question: we send a response from every controller and middleware. Why can’t we use a standard format? We should. Instead of writing res.status().json() repeatedly, we create a reusable response utility.

The problem with our current code

Our controllers and middleware each send a slightly different shape:

Health controller
res.status(200).json({
  success: true,
  message: "Secure User Management API is running"
});
User controller
res.status(200).json({
  success: true,
  count: users.length,
  data: users
});
404 middleware
res.status(404).json({
  success: false,
  message: `Route not found: ${req.method} ${req.originalUrl}`
});

This works, but we repeat the same structure in multiple places. If we later change our API response format, we must update many files.

Define one standard response format

Success response
{
  "success": true,
  "message": "Users fetched successfully",
  "data": [
    {
      "id": 1,
      "name": "Birendra Singh",
      "email": "birendra@example.com"
    }
  ]
}
Error response
{
  "success": false,
  "message": "Route not found",
  "data": null
}

We can include optional fields such as count, errors, or pagination metadata when needed. The important thing is that the core structure stays consistent.

Create a reusable response utility

src/utils/api-response.ts
import type { Response } from "express";

type ApiResponse<T> = {
  success: boolean;
  message: string;
  data: T | null;
};

export const sendResponse = <T>(
  res: Response,
  statusCode: number,
  message: string,
  data: T | null = null
): void => {
  const response: ApiResponse<T> = {
    success: statusCode < 400,
    message,
    data
  };

  res.status(statusCode).json(response);
};
PartWhat it does
ApiResponse<T>Defines our standard response structure
<T>A TypeScript generic: data can hold users, a single user, a string, or another type. When we pass an array of users, TypeScript infers the type of data
statusCodeLets us send 200, 201, 400, 404, or 500 depending on the situation
statusCode < 400Sets success to true for successful HTTP status codes and false for error codes

Use it inside our controllers

Update src/controllers/user.controller.ts:

src/controllers/user.controller.ts
import type { Request, Response } from "express";
import { getAllUsers } from "../services/user.service.js";
import { sendResponse } from "../utils/api-response.js";

export const getUsers = (_req: Request, res: Response): void => {
  const users = getAllUsers();

  sendResponse(
    res,
    200,
    "Users fetched successfully",
    users
  );
};

The controller no longer writes res.status().json() manually. The output becomes:

GET /api/users200
{
  "success": true,
  "message": "Users fetched successfully",
  "data": [
    {
      "id": 1,
      "name": "Birendra Singh",
      "email": "birendra@example.com"
    },
    {
      "id": 2,
      "name": "Rahul Sharma",
      "email": "rahul@example.com"
    }
  ]
}
The count field is gone

If we want a count, we can add it as optional metadata or include it in the response data. We should make that design decision consistently.

Can middleware use the same utility?

Yes. Middleware that sends an HTTP response can use the same utility. Update src/middlewares/not-found.middleware.ts:

src/middlewares/not-found.middleware.ts
import type { RequestHandler } from "express";
import { sendResponse } from "../utils/api-response.js";

export const notFoundHandler: RequestHandler = (
  req,
  res,
  _next
) => {
  sendResponse(
    res,
    404,
    `Route not found: ${req.method} ${req.originalUrl}`
  );
};

This returns:

GET /api/unknown404
{
  "success": false,
  "message": "Route not found: GET /api/unknown",
  "data": null
}

The same utility can be used by your error-handling middleware, login controller, registration controller, and admin routes.

Not every middleware should send a response

Logging and authentication middleware may call next() to continue processing instead. Only middleware that needs to finish the request should send a response.

One more improvement for our project

As the project grows, keep these responsibilities separate:

Controller

Decides what response to send.

Response utility

Formats the response consistently.

Client / frontend

Receives predictable JSON.

Later we can also create a standard error class and let the global error-handling middleware format errors centrally. That’s especially useful for validation errors, duplicate emails, invalid credentials, and database failures.
