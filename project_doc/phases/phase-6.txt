Phase 6.2 — Prepare the login functionality
    Before implementing login, let's understand what needs to happen when a user logs in.

    Login workflow:
        1. User submits email and password
        2. Validate request using Zod
        3. Find user by email in PostgreSQL
        4. Verify password using Argon2
        5. Generate JWT access and refresh tokens
        6. Return successful login response

    We'll implement this one piece at a time.
    
    Step 6.2.1 — Create the login validation schema
        Open:
            src/validators/auth.validator.ts

            export const loginSchema = z.object({
                email: z.string()
                    .trim()
                    .email("Please enter a valid email address")

    Phase 6.2.3 — Create a service to find a user by email
        Before checking a password, we need to retrieve the user's stored password hash from the database.
        
        1. Create src/services/user.service.ts update
            You already have a getAllUsers() function in this file. Keep it unchanged.

            Add this new function:
                export const getUserByEmail = async (email: string) => {
                    const result = await pool.query(
                        `SELECT
                            id,
                            name,
                            email,
                            password_hash,
                            is_email_verified,
                            is_active
                        FROM users
                        WHERE LOWER(email) = LOWER($1)
                        LIMIT 1`,
                        [email]
                    );

                    return result.rows[0] ?? null;
                    };
            
        2. Understand the important parts
            A. Parameterized query
                WHERE LOWER(email) = LOWER($1)

                $1 is a placeholder. The actual email is passed separately:
                    [email]

                This protects the query from SQL injection.

            B. Why password_hash?
                Our database doesn't store the original password. It stores the Argon2 hash.
                We'll retrieve that hash and compare it with the password submitted during login.

            C. Why ?? null?
                return result.rows[0] ?? null;
                    - If a matching user exists, return the user object.
                    - If no user exists, return null.
        
            D. Why are we retrieving inactive and unverified status?
                We'll use these fields to prevent inactive or unverified users from logging in.

    Phase 6.2.4 — Understand password verification using Argon2
        Before writing the login service, let's understand how password verification works.
        During registration, we used:
            const passwordHash = await argon2.hash(password, {
                type: argon2.argon2id
            });

        For example:
            During registration, User password: MySecurePassword123
            Argon2id hashing
            Database: $argon2id$v=19$...
            During login, Submitted password: MySecurePassword123
            argon2.verify()
            true — Password matches

        1. Important: We don't hash the password again and compare strings
            Argon2 uses a random salt when generating a hash. Therefore, hashing the same password again can produce a different hash.

            Instead, we use:
                const isPasswordValid = await argon2.verify(
                    user.password_hash,
                    password
                );

            Arguments:
                - First argument: stored password hash from PostgreSQL.
                - Second argument: password submitted by the user.

            It returns a boolean:
                - true — Password matches.
                - false — Password doesn't match.
        
        2. Create a temporary file:
            src/config/test-password.ts
            Add:
                import argon2 from "argon2";

                const testPassword = async (): Promise<void> => {
                    const password = "MySecureTestPassword123";

                    const passwordHash = await argon2.hash(password, {
                        type: argon2.argon2id
                    });

                    const correctPassword = await argon2.verify(
                        passwordHash,
                        password
                    );

                    const wrongPassword = await argon2.verify(
                        passwordHash,
                        "WrongTestPassword123"
                    );

                    console.log("Correct password:", correctPassword);
                    console.log("Wrong password:", wrongPassword);
                };

                testPassword();

    Phase 6.2.5 — Create the login service
        We'll keep authentication business logic inside the service layer, not inside the controller.
        
        1. Update src/services/auth.service.ts
            Add this import:
                import { getUserByEmail } from "./user.service.js";

            You already have the argon2 import in this file.
            Now add the following function below your existing registerUser() function:

            type LoginInput = {
                email: string;
                password: string;
            };

            export const loginUser = async (loginData: LoginInput) => {
                const { email, password } = loginData;

                // 1. Find user by email
                const user = await getUserByEmail(email);

                // 2. Check whether user exists
                if (!user) {
                    throw new AppError(401, "Invalid email or password");
                }

                // 3. Check whether account is active
                if (!user.is_active) {
                    throw new AppError(403, "Your account is inactive");
                }

                // 4. Check whether email is verified
                if (!user.is_email_verified) {
                    throw new AppError(403, "Please verify your email before logging in");
                }

                // 5. Verify password
                const isPasswordValid = await argon2.verify(
                    user.password_hash,
                    password
                );

                if (!isPasswordValid) {
                    throw new AppError(401, "Invalid email or password");
                }

                // 6. Return safe user information
                return {
                    id: user.id,
                    name: user.name,
                    email: user.email,
                    is_email_verified: user.is_email_verified,
                    is_active: user.is_active
                };
            };
        
        2. Understand the security decisions
            Condition	            HTTP status	Reason
            User doesn't exist	    401	Invalid credentials
            Wrong password	        401	Invalid credentials
            Account inactive	    403	Account disabled
            Email not verified	    403	Verification required
            All checks pass	—	    Return user information

            Why use the same error for missing user and wrong password?

            If we return "Email does not exist", attackers can discover which email addresses are registered.

            Returning the same 401 Invalid email or password message reduces this user-enumeration risk.

            Why return a new object instead of the database user directly?

            Because the database user contains password_hash. We must never send that field to the client.

Phase 6.3 — JWT Authentication

    We'll implement:
        1. JWT access token generation.
        2. JWT refresh token generation.
        3. Token verification.
        4. Authentication middleware.
        5. Protected API routes.

    First, let's understand the difference between access and refresh tokens.

    Access Token: Short-lived
        Used to access protected APIs, such as:
            - View profile
            - Update profile
            - Access user-specific data
        
        Example lifetime: 15 minutes

    Refresh Token: Longer-lived
        Used to obtain a new access token without asking the user to log in again.

        Example lifetime: 7 days
    
    How they work together:
        (image)

    The client sends the access token with API requests. When it expires, the client uses the refresh token to obtain a new access token.

    We'll implement refresh-token storage and rotation securely in a later step.

    Step 6.3.1 — Install JWT packages
        We'll use the jsonwebtoken library.

        Run:
            npm install jsonwebtoken
            npm install -D @types/jsonwebtoken

        Why two packages?
            - jsonwebtoken: generates and verifies JWT tokens.
            - @types/jsonwebtoken: provides TypeScript definitions.

    Step 6.3.2 — Configure environment variables
        Open your .env file and add:

            JWT_REFRESH_SECRET=replace_with_another_long_random_secret

            JWT_ACCESS_EXPIRES_IN=15m
            JWT_REFRESH_EXPIRES_IN=7d

        Use two different, cryptographically random secrets. Never use the example text as an actual secret, and never commit .env to GitHub.

    Phase 6.3.3 — Create JWT configuration
        Before generating tokens, let's centralize our JWT configuration. This avoids accessing environment variables repeatedly throughout the application.
        
        1. Create src/config/jwt.ts
            Add:

                const accessTokenSecret = process.env.JWT_ACCESS_SECRET;
                const refreshTokenSecret = process.env.JWT_REFRESH_SECRET;

                if (!accessTokenSecret || !refreshTokenSecret) {
                    throw new Error("JWT secrets are missing in environment variables");
                }

                    accessTokenSecret,
                    refreshTokenSecret,

        2. Understand the code
            A. Why check the secrets?
                if (!accessTokenSecret || !refreshTokenSecret) {
                    throw new Error("JWT secrets are missing in environment variables");
                }

                Suppose someone forgets to configure a JWT secret.
                Without this check, your application might start successfully but fail when trying to generate a token.
                We want the application to fail immediately with a clear error.

            B. Why export jwtConfig?
                export const jwtConfig = {
                    accessTokenSecret,
                    refreshTokenSecret,
                    accessTokenExpiresIn: process.env.JWT_ACCESS_EXPIRES_IN || "15m",
                    refreshTokenExpiresIn: process.env.JWT_REFRESH_EXPIRES_IN || "7d"
                };

                Other files can now import the configuration:
                    import { jwtConfig } from "../config/jwt.js";

            C. Why use ||?
                process.env.JWT_ACCESS_EXPIRES_IN || "15m"

                If the environment variable is missing or empty, the application uses 15m as the default.

    Phase 6.3.4 — Create the JWT token service
        We'll create a reusable service responsible for generating access and refresh tokens.
        1. Create src/services/jwt.service.ts
            Add the following code:
                import jwt from "jsonwebtoken";
                import { jwtConfig } from "../config/jwt.js";

                type TokenPayload = {
                    userId: string;
                };

                export const generateAccessToken = (userId: string): string => {
                    return jwt.sign(
                        { userId } satisfies TokenPayload,
                        jwtConfig.accessTokenSecret,
                        {
                            expiresIn: jwtConfig.accessTokenExpiresIn as jwt.SignOptions["expiresIn"]
                        }
                    );
                };

                export const generateRefreshToken = (userId: string): string => {
                    return jwt.sign(
                        { userId } satisfies TokenPayload,
                        jwtConfig.refreshTokenSecret,
                        {
                            expiresIn: jwtConfig.refreshTokenExpiresIn as jwt.SignOptions["expiresIn"]
                        }
                    );
                };
        
        2. Understand the important concepts
            A. What is a JWT?
                JWT stands for JSON Web Token.

                A JWT has three parts:
                    HEADER.PAYLOAD.SIGNATURE

                A JWT is commonly represented as three Base64URL-encoded sections separated by dots.

                - Header: Specifies the signing algorithm.
                - Payload: Contains information such as the user ID.
                - Signature: Allows the server to verify that the token hasn't been modified.

                Remember: JWT payloads are encoded, not encrypted. Never put passwords or sensitive personal information inside them.

            B. What is userId?
                type TokenPayload = {
                    userId: string;
                };

                We use the database user ID to identify the authenticated user.

            C. What does jwt.sign() do?
                jwt.sign(payload, secret, options);

                It creates and signs a JWT using the supplied secret.

            D. Why two different secrets?
                We use separate secrets for access and refresh tokens. This separates their signing trust and prevents a token signed for one purpose from being accepted as the other merely because they share a secret.

    Phase 6.3.6 — Create the refresh tokens table
        Why do we need another database table?

        A refresh token can remain valid for seven days. If a user logs out, changes devices, or an administrator disables their account, we need a way to revoke that token.

        We'll store a SHA-256 hash of each refresh token in PostgreSQL, not the original token.
        
        1. Create the table
            Connect to your secure_user_management database using PostgreSQL and execute:
                CREATE TABLE refresh_tokens (
                    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
                    user_id BIGINT NOT NULL,
                    token_hash TEXT NOT NULL,
                    expires_at TIMESTAMPTZ NOT NULL,
                    revoked_at TIMESTAMPTZ,
                    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
                    CONSTRAINT fk_refresh_token_user
                        FOREIGN KEY (user_id)
                        REFERENCES users(id)
                        ON DELETE CASCADE
                );
            
        2. Create indexes
            Execute:
                CREATE UNIQUE INDEX refresh_tokens_hash_unique_idx
                ON refresh_tokens(token_hash);

                CREATE INDEX refresh_tokens_user_id_idx
                ON refresh_tokens(user_id);
        
        3. Understand the columns
            Column	            Purpose
            id	                Unique token record ID
            user_id	            Identifies the token owner
            token_hash	        SHA-256 hash of the refresh token
            expires_at	        Token expiration date
            revoked_at	        When the token was revoked
            created_at	        When the token was created

            Important design decision: A user can have multiple refresh tokens because they may log in from multiple devices.

            For example:
                - Laptop — Refresh token 1
                - Mobile — Refresh token 2
                - Tablet — Refresh token 3
            
            Logging out from one device should not automatically log the user out from every other device.
        
        4. Verify the table
            Run:
                \d refresh_tokens

            You should see the table structure and indexes.

            Expected result
                The refresh_tokens table is created successfully.

    Phase 6.3.7 — Create the refresh token storage service
        Remember our security decision:
            - Generate a refresh token using JWT.
            - Hash the token using SHA-256.
            - Store only the hash in PostgreSQL.
            - Return the original token to the client.
        
        1. Update src/utils/token.ts
            You already have generateVerificationToken() in this file.

            Add this new function without changing the existing function:
                import { createHash, randomBytes } from "node:crypto";

                export const hashToken = (token: string): string => {
                    return createHash("sha256")
                        .update(token)
                        .digest("hex");
                };

            If createHash is already imported, don't import it again.
            Why are we creating a reusable function?

            We already use SHA-256 hashing for email verification tokens. Now we can reuse the same hashing logic for refresh tokens.
        
        2. Create src/services/refresh-token.service.ts
            Add:
                import pool from "../config/db.js";
                import { hashToken } from "../utils/token.js";

                type StoreRefreshTokenInput = {
                    userId: string;
                    refreshToken: string;
                };

                export const storeRefreshToken = async (
                    tokenData: StoreRefreshTokenInput
                ): Promise<void> => {
                    const { userId, refreshToken } = tokenData;

                    const tokenHash = hashToken(refreshToken);

                    await pool.query(
                        `INSERT INTO refresh_tokens (user_id, token_hash, expires_at)
                        VALUES ($1, $2, NOW() + INTERVAL '7 days')`,
                        [userId, tokenHash]
                    );
                };

        3. Understand the implementation
            A. Why hash the refresh token?
                Imagine someone gets unauthorized access to your database.

                If you store original refresh tokens, that person could potentially use them to authenticate as your users.

                By storing only their hashes, the original tokens cannot practically be recovered from the database.

            B. Why use parameterized SQL?
                [userId, tokenHash]

                This keeps user input separate from the SQL query and protects against SQL injection.

            C. Why Promise<void>?

                The function saves a record but doesn't need to return anything.
        
        4. Build the project
            npm run build

        For now, we're using a seven-day database expiration to match the JWT configuration.

        Later, we'll make token expiration and database expiration derive from one shared configuration to avoid mismatches.

Phase 6.4 — Refresh Token Validation and Rotation
    Let's understand why we need refresh tokens before writing code.
    
    1. Why do we need refresh tokens?
        Currently, our JWT configuration is:
            Token	        Expiration	    Purpose
            Access token	15 minutes	    Access protected APIs
            Refresh token	7 days	        Obtain a new access token

        Imagine this scenario:
            1. User logs in successfully.
            2. Server generates an access token and refresh token.
            3. After 15 minutes, the access token expires.
            4. User tries to access /api/users/me.
            5. Server returns 401 Unauthorized.
            6. Instead of asking the user to log in again, the client sends the refresh token to obtain a new access token.
        
        Token lifecycle
            Login
            Generate access and refresh tokens

                Access token
                15 minutes
                Protected APIs

                Refresh token
                7 days
                Renew access

            Access token expires
            Client sends refresh token

            New access token issued
    
    2. What is refresh token rotation?
        We won't reuse the same refresh token every time.

        Instead:
            - Client sends the existing refresh token.
            - Server validates it.
            - Server revokes the old refresh token.
            - Server generates a new access token and refresh token.
            - Server stores the new refresh-token hash in PostgreSQL.
            - Client replaces both old tokens with the new ones.
        
        This process is called Refresh Token Rotation.

        It also helps detect attempts to reuse an already-rotated refresh token.
        
    3. Our implementation plan
        We'll complete this phase step by step:
            Step	Task
            6.4.1	Understand refresh-token validation
            6.4.2	Create refresh-token lookup service
            6.4.3	Verify refresh JWT
            6.4.4	Implement token rotation transaction
            6.4.5	Create refresh-token controller
            6.4.6	Create refresh route
            6.4.7	Test rotation in Postman
            6.4.8	Test expired, invalid and reused tokens

    Step 6.4.1 — Understand the validation process
        Before coding, understand that JWT signature verification alone is not enough.

        We must check two things:
            1. Is the refresh JWT valid and unexpired?
            2. Does its SHA-256 hash exist in refresh_tokens, with revoked_at IS NULL and expires_at > NOW()?
    
        Why the database check?

        Suppose someone steals a refresh token. Even if its JWT signature is valid, we need the ability to revoke it immediately.

        That's why we store its hash in PostgreSQL.

    Phase 6.4.4 — Implement refresh-token rotation using a PostgreSQL transaction
        We'll create a function that performs three database operations safely:
            1. Find and lock the existing refresh-token record.
            2. Revoke the old refresh token.
            3. Store the new refresh-token hash.

        All three operations must happen inside one PostgreSQL transaction.
        
        Step 1: Update src/services/refresh-token.service.ts
            Keep your existing storeRefreshToken() and findValidRefreshToken() functions.

            Add these imports if they aren't already present:
                import jwt from "jsonwebtoken";
                import { AppError } from "../utils/app-error.js";
            
            Now add this function:

                type RotateRefreshTokenInput = {
                    userId: string;
                    oldRefreshToken: string;
                    newRefreshToken: string;
                };

                export const rotateRefreshToken = async (
                    tokenData: RotateRefreshTokenInput
                ): Promise<void> => {
                    const { userId, oldRefreshToken, newRefreshToken } = tokenData;

                    const oldTokenHash = hashToken(oldRefreshToken);
                    const newTokenHash = hashToken(newRefreshToken);

                    const decoded = jwt.decode(newRefreshToken);

                    if (
                        typeof decoded !== "object" ||
                        decoded === null ||
                        typeof decoded.exp !== "number"
                    ) {
                        throw new Error("Invalid new refresh token expiration");
                    }

                    const expiresAt = new Date(decoded.exp * 1000);

                    const client = await pool.connect();

                    try {
                        await client.query("BEGIN");

                        const result = await client.query(
                            `SELECT id
                            FROM refresh_tokens
                            WHERE token_hash = $1
                                AND user_id = $2
                                AND revoked_at IS NULL
                                AND expires_at > NOW()
                            FOR UPDATE`,
                            [oldTokenHash, userId]
                        );

                        if (result.rowCount === 0) {
                            throw new AppError(401, "Invalid or expired refresh token");
                        }

                        await client.query(
                            `UPDATE refresh_tokens
                                SET revoked_at = NOW()
                            WHERE id = $1`,
                            [result.rows[0].id]
                        );

                        await client.query(
                            `INSERT INTO refresh_tokens (
                                user_id,
                                token_hash,
                                expires_at
                            )
                            VALUES ($1, $2, $3)`,
                            [userId, newTokenHash, expiresAt]
                        );

                        await client.query("COMMIT");
                    } catch (error) {
                        await client.query("ROLLBACK");
                        throw error;
                    } finally {
                        client.release();
                    }
                };
        
        Step 2: Understand three important concepts
            1. Database transaction
                await client.query("BEGIN");
                Starts a transaction.
    
                await client.query("COMMIT");
                Saves all database changes.
    
                await client.query("ROLLBACK");
                Cancels the changes if something fails.

                For example, if the old token is revoked but inserting the new token fails, the rollback restores the old token's unrevoked state.

            2. FOR UPDATE
                FOR UPDATE

                Locks the matching database row until the transaction finishes.

                This helps prevent two simultaneous requests from successfully rotating the same refresh token.

            3. Actual JWT expiration
                const expiresAt = new Date(decoded.exp * 1000);

                Instead of assuming every refresh token expires after seven days, we read its actual JWT expiration.

                This keeps the database expiration synchronized with the token configuration.
        
            Step 3: Build the project
                Run: npm run build

                    throw new AppError(401, "Invalid or expired refresh token");
                }

                // 3. Check current user status
                const user = await getUserAuthStatus(decoded.userId);

                if (!user) {
                    throw new AppError(401, "User account not found");
                }

                if (!user.is_active) {
                    throw new AppError(403, "Your account is inactive");
                }

                if (!user.is_email_verified) {
                    throw new AppError(403, "Please verify your email first");
                }

                // 4. Generate new tokens
                const newAccessToken = generateAccessToken(decoded.userId);
                const newRefreshToken = generateRefreshToken(decoded.userId);

                // 5. Rotate the refresh token
                await rotateRefreshToken({
                    userId: decoded.userId,
                    oldRefreshToken: refreshToken,
                    newRefreshToken
                });

                // 6. Return new tokens
                return {
                    accessToken: newAccessToken,
                    refreshToken: newRefreshToken
                };
            };

        Step 3: Understand an important security detail
            Why are we checking the database twice?
            - findValidRefreshToken() checks whether the token is currently valid.
            - rotateRefreshToken() checks again inside a transaction and locks the database row using FOR UPDATE.
            This second check is important because another request could rotate the same token between those two operations.

            Only one request should successfully rotate it.

Phase 6.6 — Immediate Logout & Session Management

    Step 6.6.1 — Design the session-management database structure
        1. Why do we need a sessions table?
            Currently, your refresh_tokens table stores individual refresh tokens.

            But we need to track each login session independently.

            For example:
                Device	    Session	Status
                Laptop	    Session 101	Active
                Mobile	    Session 102	Active
                Tablet	    Session 103	Revoked

            If the user logs out from their laptop, we revoke Session 101 only. The mobile and tablet sessions remain active.

        2. New database table: user_sessions
            We'll create a table to manage individual login sessions.

            CREATE TABLE user_sessions (
                id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
                user_id BIGINT NOT NULL,
                created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
                expires_at TIMESTAMPTZ NOT NULL,
                revoked_at TIMESTAMPTZ,
                last_used_at TIMESTAMPTZ,
                user_agent TEXT,
                ip_address INET,
                CONSTRAINT fk_user_sessions_user
                    FOREIGN KEY (user_id)
                    REFERENCES users(id)
                    ON DELETE CASCADE
            );
        
        3. Create indexes
            These will help us find a user's active sessions efficiently.
            CREATE INDEX user_sessions_user_id_idx
            ON user_sessions(user_id);

            CREATE INDEX user_sessions_active_idx
            ON user_sessions(user_id, expires_at)
            WHERE revoked_at IS NULL;
        
        4. Connect refresh tokens with sessions
            One session can have multiple refresh-token records because we rotate refresh tokens.

            We'll add a session_id column to your existing refresh_tokens table:
                ALTER TABLE refresh_tokens
                ADD COLUMN session_id BIGINT
                REFERENCES user_sessions(id)
                ON DELETE CASCADE;

            We'll initially allow NULL because your existing refresh-token records don't have a session associated with them. New login sessions will populate this column.
            
            Our new database relationship
                users
                One user can have multiple sessions

                user_sessions
                One session per login/device

                refresh_tokens
                Multiple rotated tokens can belong to one session

        Now we'll modify the login flow so that every successful login creates a separate session.

        Our intended flow will be:
            1. User logs in with email and password.
            2. Create a session in user_sessions.
            3. Generate JWTs containing both userId and sessionId.
            4. Store refresh token with its corresponding session_id.
            5. Return tokens to the client.
        
        Later, our authentication middleware will check whether the session is still active. This is what will allow immediate logout.

            export const logoutUser = async (refreshToken: string): Promise<void> => {
                // 1. Verify refresh token
                let decoded: { userId: string; sessionId: string };

                try {
                    decoded = verifyRefreshToken(refreshToken);
                } catch {
                    throw new AppError(401, "Invalid or expired refresh token");
                }

                // 2. Find the refresh token in the database
                const storedToken = await findValidRefreshToken(refreshToken);

                if (
                    !storedToken ||
                    String(storedToken.user_id) !== decoded.userId ||
                    String(storedToken.session_id) !== decoded.sessionId
                ) {
                    throw new AppError(401, "Invalid or expired refresh token");
                }

                // 3. Start database transaction
                const client = await pool.connect();

                try {
                    await client.query("BEGIN");

                    // 4. Revoke the current login session
                    const sessionResult = await client.query(
                        `UPDATE user_sessions
                        SET revoked_at = NOW()
                        WHERE id = $1
                        AND user_id = $2
                        AND revoked_at IS NULL
                        AND expires_at > NOW()
                        RETURNING id`,
                        [decoded.sessionId, decoded.userId]
                    );

                    if (sessionResult.rowCount === 0) {
                        throw new AppError(401, "Session has expired or been revoked");
                    }

                    // 5. Revoke all refresh tokens belonging to this session
                    await client.query(
                        `UPDATE refresh_tokens
                        SET revoked_at = NOW()
                        WHERE session_id = $1
                        AND revoked_at IS NULL`,
                        [decoded.sessionId]
                    );

                    // 6. Save database changes
                    await client.query("COMMIT");

                } catch (error) {
                    await client.query("ROLLBACK");
                    throw error;

                } finally {
                    client.release();
                }
            };
